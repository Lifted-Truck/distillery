# LIBRARY — durable, evidence-backed lessons

Long-term memory for this project's knowledge loop. **Repo-shared
agent-process lessons only** — the hard-won, evidenced "how to work in this
repo without re-tripping a wire." Not decisions (→ DECISIONS.md), not task
state (→ ROADMAP.md), not machine-local facts (→ the human's global memory).

Entries are retrieved via [INDEX.md](INDEX.md). Format is `library-entry.3`
(canonical contract: `autonomous/kit/contracts/library-entry.md`). New
lessons enter as `tier: candidate` and become `canonical` on a second
independent occurrence or human review. Every entry states its own
**falsifier** — the observation that would retire it.

Note the recursion: distillery sweeps every project's LIBRARY, including
this one. These entries enter the stream this project operates.

**Entry template**

```
[Lxxxx] <title> | tier: … | added: YYYY-MM-DD | tags: … | lesson: … | evidence: … | falsifier: … | supersedes: —
```

[L0001] Noticing a missing gate is not having one — only the mechanism closes it | tier: candidate | added: 2026-08-18 | tags: gate-discipline, harness | lesson: When a session identifies a missing safety check and files it as a follow-up task rather than installing it immediately, the check does not exist and the repo keeps reading as compliant. A backlog item is a record of intent; a gate is a mechanism. If the check is cheap enough to describe accurately, it is usually cheap enough to install in the same change — and if it genuinely is not, the honest move is to record the repo as UNGATED in its status surface rather than as having a known gap. | evidence: 2026-08-18 — this repo self-identified that its verify carried no leak_gate, spawned a background task for it, and continued. The task was never closed. Days later the fleet audit independently found the same repo ungated while it declared a kit_version promising the gate; the gate was installed only when the kit vendored it. | falsifier: a repo that records a missing gate as a task, does not install it, and is nonetheless protected against the failure the gate prevents. | supersedes: —

[L0002] A design review that RUNS the design finds what reading it cannot | tier: candidate | added: 2026-08-18 | tags: review-discipline, oracle-discipline | lesson: Adversarial review by reading catches contradictions and unstated assumptions; it does not catch a strategy that is coherent, well-argued, and empirically useless on the actual data. Give a reviewer of any data-processing design the standing instruction to EXECUTE the proposed algorithm over the real corpus before judging it, and to report coverage as a number. The cost is minutes; the failure it prevents is shipping a plausible design that finds nothing. | evidence: 2026-08-18 — a D3 bundling strategy (partition the lesson corpus by tag) read as sound through a full design pass. A critic that prototyped it over the committed 138-lesson stream found it reached 43 lessons (31 percent) and located NONE of the three recurrences the project had already proven exist, because human-authored tag vocabularies are project-local and never collide across projects. | falsifier: a data-processing design flaw of this class (coherent but empirically empty) caught reliably by reading alone, without executing the strategy over real data. | supersedes: —

[L0003] A design doc's factual claims must be computed, not recalled — an invented justification hides the flaw beneath it | tier: candidate | added: 2026-08-18 | tags: provenance, review-discipline | lesson: When a design document asserts a specific, checkable fact about the corpus as its justification, that fact must be computed at writing time and the computation cited. An invented-but-plausible justification is worse than an absent one, because it terminates the inquiry that would have found the real problem: the author stops looking once the reasoning reads as settled. Treat any uncited corpus claim in a design as a hypothesis and mark it as such. | evidence: 2026-08-18 — a D3 design justified its bundling strategy by naming three tags said to span a known lesson family. None of the three appeared on any of those records; they belonged to unrelated projects. The fabricated justification is precisely why the strategy's 31-percent coverage hole went unnoticed through a full authoring pass and into review. | falsifier: an uncited, incorrect factual claim in a design document that provably did not obscure any downstream defect. | supersedes: —

[L0004] When a format is still being ruled on, ship the machinery and hold the data | tier: candidate | added: 2026-08-18 | tags: stream-schema, provenance | lesson: For data bound for an append-only or public store whose schema is still under active ruling, commit the code and withhold the corpus. Machinery is revisable; committed data in an append-only store is not, and a leaked or mis-shaped record persists in history even after the format is fixed. The cost of holding is a delay; the cost of committing early is a history rewrite, or a permanent superseded record on day one. | evidence: 2026-08-18 — this project held its genesis journal uncommitted through two contract rulings. When an absolute-path leak was found in the record shape, the fix was a one-line edit and a regeneration. A sibling project that had committed the equivalent data first had to rewrite git history to purge the same class of leak. | falsifier: an append-only or public store where committing data before its schema was ratified cost no more than a forward-only edit. | supersedes: —

[L0005] A response filed in the provider's tree does not reach the consumer | tier: candidate | added: 2026-08-18 | tags: integrations, provenance | lesson: In a file-based brief/response protocol, the answer lands in the PROVIDER's repository. Nothing in the consumer's own tree changes when it arrives, so an answered thread and an ignored one are indistinguishable from the consumer's side until someone deliberately pulls and reads the provider's mailbox. Make reading the provider's tree an explicit step at session start, not an event you wait to be told about. | evidence: 2026-08-18 — a contract ruling this project had asked for was filed on 2026-08-10 and sat unread for eight days; a follow-up brief was filed on 2026-08-12 listing the already-ruled items as still open, and the parser continued implementing the superseded contract version. | falsifier: a file-based exchange protocol in which a consumer reliably notices a response without deliberately reading the provider's tree. | supersedes: —
